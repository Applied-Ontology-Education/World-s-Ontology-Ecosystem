## Major modeling decisions

1. **The procedure is information, not an event.**
   - "Every 30 days" is a prescription, not a time period, so it's an `IntervalSpecification` that is part of the plan specification.
   - The procedure connects to Inspection 17 through the usual IAO/OBI pattern: the procedure is concretized as a plan that Alex bears, and Inspection 17 realizes that plan. This avoids pointing an instance-level "is about" at the class *Pump*.
   - Whether this inspection complied with the 30-day interval can't be checked, because the scenario gives no dates. That check belongs in SPARQL or SHACL once timestamps exist.
2. **"Technician" is a role, not a subclass of person.** Alex remains a `Person` and bears a `TechnicianRole`, which the inspection realizes. Alex keeps his identity if he changes jobs.
3. **Vibration is a process.** A velocity of 4.2 mm/s describes motion, which is an occurrent. The BFO OWL release has no qualities of processes, so `M_17` *is about* `Vib_P17` instead of using "is quality measurement of". The unit and value sit on the datum; the pump itself carries no number.
4. **"Requires bearing replacement" is a claim, not a property.** The report *states* a need, so the need is modeled as a finding (`F_17`) that is part of `R_17`. The pump doesn't get a quality called "needs replacement". If you later want to capture the physical reason, add a degradation disposition that inheres in the bearing.
5. **The requested replacement is not an individual.** W-22 requests an event that hasn't happened, so asserting a `BearingReplacement` individual, or using `W_22 prescribes some BearingReplacement`, would wrongly state that it exists. Instead, W-22 has an action specification whose class records what kind of action is wanted and whose "is about" link names the target. If the replacement is carried out later, its process individual would realize a plan that concretizes W-22.
6. **The bearing is an added individual.** The scenario never names one. `P_17_Bearing` exists so the finding and the work order have a precise target. If you'd rather not introduce entities the source doesn't mention, point both at `P_17` instead.
7. **The chain between documents is provenance.** `W_22 prov:wasDerivedFrom F_17` captures "requests that replacement". The fuller alternative is a work-order issuance process with `F_17` as input and `W_22` as output.
8. **Uncertain identifiers are left out.** I used only BFO, IAO, OBI and RO terms whose IDs I'm confident of. `hasAgent` is local and can be mapped to a CCO or OBI agent relation.

**In plain terms:** The pump, the bearing and Alex are physical things. The inspection and the vibration are things that happened. The procedure, the report, the measurement, the "needs a new bearing" finding and the work order are all documents or pieces of information. The replacement is only requested, not done, so the model describes the request without pretending the repair took place.
